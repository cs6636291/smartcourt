นักศึกษาต้องตรวจทานขอบเขตและคำอธิบายให้ตรงกับระบบที่สาธิต และรับผิดชอบฉบับส่งอาจารย์ เอกสารนี้อ้างอิงโค้ดปัจจุบันและ PDF Requirement ที่ให้ตรวจ

1. ขอบเขตและผู้ใช้งาน

Backend: Django REST Framework, Frontend: React และ Tailwind CSS, ฐานข้อมูล SQL: SQLite ผู้ใช้ทั่วไปดูสถานะสนาม นักศึกษาสมัครและจองสนาม ผู้ดูแลจัดการข้อมูลผ่าน Django Admin ที่ /admin/ ผู้ดูแลต้องมีสิทธิ์ staff และสิทธิ์ของโมเดลที่เกี่ยวข้อง หรือเป็น superuser

2. Use Case Diagram

เส้นทึบแสดงบทบาทที่ใช้ฟังก์ชันได้ การสมัครสมาชิกมีเงื่อนไขว่าต้องยืนยัน OTP ก่อน ส่วนการจองและแก้โปรไฟล์ต้องเข้าสู่ระบบ การจัดการผ่าน Admin ไม่ได้เป็นหน้า React ของนักศึกษา

3. ข้อกำหนดและกฎธุรกิจ

  1. รับจองตั้งแต่วันนี้ถึงอีก 4 วัน รวม 5 วันตามเวลา Asia/Bangkok
  2. ช่วงเวลาเริ่ม 08:00 ถึง 19:00 ครั้งละ 1 ชั่วโมง สิ้นสุดไม่เกิน 20:00 และวันนี้ห้ามจองช่วงที่เริ่มไปแล้ว
  3. ผู้ใช้มีการจอง confirmed ได้สูงสุด 1 รายการต่อวัน เมื่อยกเลิกแล้วสามารถจองใหม่ได้
  4. สนามเดียวกัน วันและเวลาเดียวกัน มีการจอง confirmed ได้เพียงรายการเดียว
  5. สนามว่างเมื่อไม่มี confirmed ที่ทับช่วงเวลาที่เลือก รายการ cancelled เป็นประวัติ ไม่ได้ยืนยันว่าช่วงนั้นยังว่าง
  6. การยกเลิกเปลี่ยนสถานะเป็น cancelled ไม่ลบรายการจริง สมาชิกยกเลิกได้เฉพาะรายการของตนเอง
  7. รหัสผ่านอย่างน้อย 8 ตัว มีตัวอักษรอังกฤษและตัวเลข อีเมลและรหัสนักศึกษาไม่ซ้ำ Backend บังคับรหัสนักศึกษา ASCII 13 หลักและชื่อ/นามสกุลไม่ว่าง อีเมลโปรไฟล์ล็อกตามบัญชีที่ยืนยัน
  8. OTP อายุ5นาที ผิดได้ไม่เกิน5ครั้ง ขอซ้ำมี cooldown และจำกัด email/IP เมื่อผ่านแล้วใช้ verification_token ผูกอีเมล อายุ10นาที ใช้สมัครได้ครั้งเดียว ไม่มี OTP ใน API/log แอป ส่งเมลไม่ได้ตอบ503
  9. ออกจากระบบเพิกถอน refresh token และล้าง session ในหน้าเว็บ access token ที่ออกก่อนหน้ายังมีอายุได้ถึง30นาทีตาม JWT

4. รายละเอียด Use Case

รหัส/ผู้ใช้เงื่อนไขก่อนทำและขั้นตอนหลักผลสำเร็จ / กรณีผิดพลาด
UC01 Guest/นักศึกษาเปิดหน้าหลัก → เลือกวันและเวลา → ดูสถานะสนามแสดงสถานะตาม API; วันหรือเวลาไม่ถูกต้องต้องแจ้งข้อผิดพลาด
UC02 Guestกรอกอีเมล → ขอ OTP → กรอกรหัสยืนยันOTP ถูกต้องได้รับ verification_token ผูกอีเมล อายุ10นาทีใช้ครั้งเดียว; OTP อายุ5นาที ผิดเกิน5ครั้งถูกล็อก ส่งเมลไม่ได้แจ้งข้อผิดพลาดโดยไม่คืนรหัส
UC03 Guestผ่าน OTP → กรอกชื่อ นามสกุล ชื่อเล่น เพศ รหัสนักศึกษา รหัสผ่าน → ยืนยันบันทึกสมาชิกและหน้าเว็บเข้าสู่ระบบต่อ; อีเมลล็อกตามขั้นแรก ข้อมูลซ้ำ/ไม่ผ่านเกณฑ์แสดงข้อผิดพลาด
UC04 Guestกรอกอีเมลและรหัสผ่าน → เข้าสู่ระบบได้รับ JWT และไปหน้าหลัก; ข้อมูลผิดไม่อนุญาตเข้าระบบ
UC05 นักศึกษาเข้าสู่ระบบ → หน้าจอง → เลือกชั้น วัน และเวลาแสดงเวลาจองได้; วันที่มีการจองของตนเองแล้วปิดสิทธิ์จองเพิ่ม
UC06 นักศึกษามีสิทธิ์จอง → เลือกเวลาว่าง → ตรวจรายละเอียด → ยืนยันบันทึก Appointment เป็น confirmed และโหลดข้อมูลใหม่; จองซ้ำ/เกินสิทธิ์/นอกช่วงเวลาปฏิเสธที่ Backend
UC07 นักศึกษาเข้าสู่ระบบ → ดูรายการของตนเองบนหน้าหลัก/หน้าจองแสดงรายการ confirmed ของตนเอง; API ประวัติส่งข้อมูลเฉพาะเจ้าของ
UC08 นักศึกษาเลือกรายการตนเอง → กดยกเลิก → ตรวจรายละเอียดใน popup → ยืนยันเปลี่ยนเป็น cancelled และคืนสิทธิ์; ย้อนกลับไม่ยกเลิก รายการคนอื่น/ยกเลิกแล้วปฏิเสธ
UC09 นักศึกษาโปรไฟล์ → แก้ข้อมูล → บันทึก หรือกดออกจากระบบบันทึกข้อมูลผ่าน API; ข้อมูลผิด/ซ้ำแจ้งข้อผิดพลาด ออกจากระบบล้าง session ในหน้าเว็บ
UC10 Adminเข้าสู่ /admin/ ด้วยสิทธิ์เหมาะสม → เพิ่ม/ดู/แก้ไข/ลบสนามข้อมูลสนามเปลี่ยนในฐานข้อมูล; การลบสนามมีผลลบรายการจองที่เกี่ยวข้องตาม CASCADE ต้องพิจารณาก่อนทำ
UC11 AdminAdmin → รายการจอง → ค้นหา/กรอง → จัดการตามสิทธิ์จัดการข้อมูลและสถานะ; กฎในโมเดลยังตรวจสอบก่อนบันทึก
UC12 AdminAdmin → Users → จัดการผู้ใช้ กลุ่ม และสิทธิ์บัญชี/สิทธิ์ถูกบันทึกตามระบบ Django; ผู้ไม่มีสิทธิ์ไม่สามารถจัดการ

5. Flow ที่ใช้สาธิต

สมัคร: อีเมล → ขอ OTP → ยืนยัน OTP → ข้อมูลสมาชิก → บันทึก → เข้าสู่ระบบ → หน้าหลัก

จอง: เข้าสู่ระบบ → เลือกวัน/เวลา/สนาม → ตรวจรายละเอียด → ยืนยัน → บันทึก confirmed → แสดงรายการของตนเอง

ยกเลิก: รายการของตนเอง → popup ยืนยัน → ยืนยัน → เปลี่ยน cancelled → โหลดสถานะและสิทธิ์ใหม่

CRUD สนาม: Admin → Courts → เพิ่ม → ตรวจรายการ → แก้ไข → ตรวจข้อมูล → ลบข้อมูลทดสอบ

6. นอกขอบเขตปัจจุบัน

ชำระเงิน อัปโหลดรูปโปรไฟล์ ระบบอนุมัติโดยเจ้าหน้าที่ การแจ้งเตือนก่อนใช้งาน และการจองต่อเนื่องหลายชั่วโมง ยังไม่มีในระบบนี้

# Real SmartCourt E2E tests

These tests launch their own frontend on port 5199 and Django API on port 8099.
Each run creates a fresh, marked directory under the operating-system temporary
directory, migrates an isolated SQLite database, and seeds two test users and two
courts. Existing development servers are never reused. No development database
or real SMTP mailbox is changed.

Run from `frontend` after installing dependencies:

```powershell
npm run test:e2e
```

Install the browser once if Playwright requests it:

```powershell
npx playwright install chromium --only-shell
```

`E2E_PYTHON` can select a Django-enabled Python interpreter (default is the
project's `backend/venv/Scripts/python.exe`). `E2E_BROWSER_EXECUTABLE` can select
an already installed compatible Chromium executable. Leave `E2E_DATA_DIR` unset
for normal runs so that every run gets a fresh database.

The file email backend captures the actual message generated by the application;
the registration test reads its OTP as a test mailbox recipient would. API calls,
authentication, validation, database writes and browser pages are real; there are
no API interceptions or mocked response bodies.

| ID | Verified behavior |
| --- | --- |
| E2E01 | Register via email and OTP, lock verified email, logout, log in again |
| E2E02 | Book, reload persisted state, see both summaries, back out of cancellation, cancel and rebook |
| E2E03 | Save profile into database, reload, retain data and locked email |
| E2E04 | Two real accounts send simultaneous requests: only one succeeds; foreign cancellation and foreign history are denied |
| E2E05 | 375×480 mobile viewport: booking, centered cancel dialog, internal scrolling, reachable buttons, no horizontal overflow |

Results are written to `docs/e2e-results.json` and `docs/e2e-report/index.html`.
Failure screenshots and traces live in `frontend/test-results`. The temporary
database and captured test emails remain only as diagnostic artifacts in the
temporary directory; they contain generated test accounts, not production data.
This verifies email generation, not deliverability through a production SMTP
provider. E2E04 is a two-request concurrency check, not a load/stress test.
